## 0. 执行摘要

### 0.1 一句话结论

**方向对，但还不能直接卖。** "ZIP 本身必须激活"比旧方案好很多；Supabase 建议**合并成一个生产 project**并升级 Pro；但真正会让你出事的，大概率不是数据库，而是：**客户端可被破解、退款/争议没有流程、支付机构对产品类型的审查、目标网站改版导致产品失效后的集体退款，以及手机通知服务的长期运营成本。**

### 0.2 对你三个核心担忧的直接回答

| 你的担忧 | 简短回答 |
|---|---|
| Supabase 会不会有问题？ | 会。最大问题是**Free 计划 7 天无活动自动暂停**（暂停期间激活/验证全部失效），其次是两个 project 的密钥池容易**对不上账**。建议：生产合并为 1 个 project + 升级 Pro（约 US$25/月）+ 另开 1 个免费 dev project 做测试。 |
| 整个付款→密钥系统会不会有问题？ | 会，常见的 5 类：① webhook 重复/丢失导致**重复发 key 或付了钱没 key**；② 退款后 key 没被吊销；③ ToyyibPay 回调被伪造（要二次校验）；④ 卡网卖出的 key 与你数据库状态不一致；⑤ 没有对账机制，出了问题没人发现。 |
| 很多用户退款怎么办？ | 退款不可避免，要**提前把它做成"流程"而不是"事故"**：明确退款政策、退款即自动吊销 key、保存激活日志作为争议证据、预留准备金、控制争议率（卡组织对争议率有监控）。详见第 6 节。 |

### 0.3 Top 10 风险（详细见第 11 节）

| # | 风险 | 严重度 | 一句话 |
|---|---|---|---|
| 1 | 支付机构/平台对产品类型的审查 | 🔴 P0 | 向 Stripe 等描述产品必须与真实功能一致，否则被封号+冻结资金比"被拒绝"严重得多（HitPay 已拒绝过一次，这是信号） |

| 8 | 手机通知服务的人工开通与长期成本 | 🟠 P1 | 人工开通不可扩展；订阅型服务需要持续的服务器、监控、续费/到期自动化 |
| 9 | 卡网是匿名渠道 | 🟠 P1 | 你拿不到买家联系方式 → 客服、退款、通知更新都很难；平台本身也可能封店/调整规则 |
| 10 | 单人运维 + AI 生成代码未经独立审计 | 🟠 P1 | 支付/授权代码属于"出错成本高"的类别，必须做独立审查与测试 |

## 1. 我理解的系统与假设

### 1.1 业务模式（新方案）

```
                 ┌────────────── 销售渠道 ──────────────┐
                 │                                      │
        自建网站（Next.js / Vercel）            368云寄售（卡网，第三方）
        Stripe + ToyyibPay 收款                 支付宝/微信等（由卡网收款）
                 │                                      │
        支付成功 → 生成/分配 key              买家付款 → 卡网自动发放你预先上传的 key
                 │                                      │
                 └───────────────┬──────────────────────┘
                                 ▼
                     用户下载 ZIP → 加载扩展 → 输入 key 激活
                                 │
                 ┌───────────────┴────────────────┐
                 ▼                                ▼
       基础功能（自动打卡）                 付费功能：手机通知服务
       （激活后才可使用）                  （服务器为用户开通，订阅制）
```

### 1.2 我的假设（请逐条确认或纠正）

| 编号 | 假设 | 若不成立会怎样 |
|---|---|---|

## 2. 旧方案 vs 新方案：优缺点

### 2.1 旧方案（ZIP 无验证 + 仅付费功能用 key）

| 优点 | 缺点 |
|---|---|
| 实现简单，上线快 | **一个人买，全班都能用**——收入上限极低 |
| 基础功能无依赖，服务器宕机不影响用户 | 无法统计真实用户数，无法通知更新 |
| 几乎没有退款后"收回权限"的问题 | 无法区分正版/盗版，无法封禁滥用者 |
| 对 Supabase 的依赖低 | 付费功能转化率会很低（基础功能已够用） |

### 2.2 新方案（ZIP 本身需 key 激活 + 手机通知服务另行开通）

| 优点 | 缺点 / 新增风险 |
|---|---|
| 能限制"一个 ZIP 无限人用" | **所有用户都依赖你的验证服务**：服务挂 = 全体不可用 |
| 有真实的用户/设备数据，可做更新通知、公告、远程停用 | 客户端验证**可被破解**（见 4.4） |
| 退款后可以吊销权限 | 新增大量边界情况：换设备、重装、过期、续费、退款 |
| 可以做学期/年度订阅，收入更可预测 | 客服量上升（"激活不了""换电脑了"是最高频问题） |
| 服务端功能（手机通知）天然防盗用 | 手机通知"服务器开通"若靠人工，会成为瓶颈与出错点 |
| 可以收集匿名使用统计，判断产品健康度 | 若采集个人资料，要承担隐私合规责任 |

**结论**：新方案是正确方向，但它把你从"卖一个文件"变成了"运营一个持续在线的服务"。**责任、成本、客服都会上一个台阶**，这是第一次创业最容易低估的部分。

## 3. Supabase：要不要合并成一个 project

### 3.1 为什么现在是两个（推测）

- 网站有自己的数据库（订单、用户、支付状态）。
- 扩展需要一个"验证 key"的后端，你另开了一个 project，把**卡网上架的 key 池**放进去。
- 结果：**同一批 key 的"真相"分散在两处**。你已经遇到的症状——"China-region keys 能激活，global keys 不能，因为扩展那边的 Supabase 没有网站的 key CSV"——就是这个结构的典型后果。

### 3.2 结论

> **建议：生产环境合并为 1 个 Supabase project，再加 1 个独立的 dev/staging project。**
> 不是"为了省事合并"，而是为了让 **key / 订单 / 退款 / 设备激活** 有且只有一个事实来源（single source of truth）。

### 3.3 合并 vs 不合并

| 维度 | 合并为 1 个 | 保持 2 个 |
|---|---|---|
| 数据一致性 | ✅ 一张 `license_keys` 表，一个状态机 | ❌ 两套状态要靠人同步，退款/吊销极易遗漏 |
| 对账 | ✅ 一条 SQL 就能看"卖了多少/激活多少/退了多少" | ❌ 要跨库导出比对 |
| 运维成本 | ✅ 备份、监控、轮换密钥只做一次 | ❌ 成本×2；两个都要付费才不会暂停 |
| 权限隔离 | ⚠️ 需要靠 RLS、schema、角色隔离（做得好完全可行） | ✅ 物理隔离，一个泄漏不直接影响另一个 |
| 故障爆炸半径 | ❌ 一个 project 出问题，网站+激活一起受影响 | ✅ 互不影响 |
| 费用（Pro） | ✅ 约 US$25/月/组织（含一个 Micro 实例额度） | ❌ 第二个 project 需要额外计算资源费用，或继续用 Free（有暂停风险） |
| 迁移工作量 | ❌ 需要一次性迁移与回归测试 | ✅ 无 |

> 对你当前规模（早期、单人运维），**一致性与对账能力的价值远大于物理隔离的价值**。物理隔离的好处，用 schema + RLS + 最小权限可以拿回大部分。

### 3.4 推荐拓扑

```
Supabase 组织（Pro）
 ├── project: prod        ← 网站 + 激活 + 订单 + 授权，唯一生产库
 └── project: dev         ← Free 即可，用来测试支付/webhook/迁移（可被暂停无所谓）

prod 内部：
 ├── schema public      ← 仅放必须被前端读取的少量表（几乎为空）
 ├── schema private     ← 订单、key、授权、审计日志（不暴露给 anon）
 └── Edge Functions     ← 激活/验证/续期接口（扩展只能调用这些，不能直接查表）
```

### 3.5 Free vs Pro（✅ 已核对公开页面，2026-10）

| 项目 | Free | Pro |
|---|---|---|
| 价格 | $0 | 约 US$25/月/组织（另有用量计费，默认带花费上限） |
| 不活跃暂停 | **7 天无活动自动暂停**，需手动恢复 | 不暂停 |
| 备份 | 无自动备份 | 每日备份，保留 7 天 |
| 数据库容量 | 500 MB/项目 | 8 GB/项目（含） |
| 时间点恢复（PITR） | 无 | 需另购附加项 |

**对你的意义**
- 激活系统是"生产系统"。Free 暂停 = **所有用户同时无法验证**，这不是性能问题，而是**事故**。
- 没有备份 = 一条误删的 SQL 就可能让你丢掉所有 key 状态。**这一项就足以让你付 $25**。
- 即使你在卖 key 的同时才发现 project 被暂停，恢复通常可以，但你的客户体验已经受损。

### 3.6 迁移步骤建议

1. 在 dev project 完整演练一次（不要直接动生产）。
2. 设计统一的 `license_keys` 表（见第 12 节），增加 `channel`（website / kawang）、`region`（cn / global）、`batch_id` 字段。
3. 导入 CSV：你遇到的"数据与表结构不兼容"，通常是列类型/列名/空值/布尔与枚举格式不一致造成的。**建议先导入到一张全部为 `text` 的临时表（staging），再用 SQL 清洗后 `INSERT ... SELECT` 到正式表**，比直接导入稳得多。
4. 导入后做核对：行数、状态分布、hash 唯一性、各渠道数量。
5. 扩展指向新的统一验证接口；旧 project 保留只读一段时间（至少 30 天）再下线。
6. 切换时机选在低峰期，并准备回滚方案。

### 3.7 Supabase 安全红线

- `anon` key 一定会出现在 ZIP/网站前端里，**视为公开**；`service_role` key **绝不能**出现在 ZIP、前端代码、`NEXT_PUBLIC_*` 变量里。
- **所有表必须开启 RLS**；`license_keys`、`orders`、`payments` 对 `anon`/`authenticated` 默认**零权限**。
- 扩展不要直接 `select` 任何表，只调用 Edge Function / RPC，并在服务端做限流与校验。
- Dashboard、Vercel、Stripe、GitHub、域名注册商、邮箱：**全部开启 2FA**。邮箱是整个系统的"根信任"，被盗 = 全部沦陷。

## 4. 密钥激活系统设计评估

### 4.1 Key 生命周期（建议状态机）

```
generated → listed(已上架/可售) → sold → activated → (expired | revoked | refunded)
                                             │
                                             └─ 解绑设备 → 重新激活（受次数限制）
```

每次状态变化写入 `audit_log`（谁、何时、为什么、IP）。**没有审计日志，就没有争议证据，也没有排查依据。**

### 4.2 Key 生成与存储

| 项目 | 建议 | 说明 |
|---|---|---|
| 熵 | 至少 ~80 bit（例如 16–20 位 Base32 字符） | 你从 6 位数字改为长随机 key 是正确的 |
| 字符集 | 去掉易混淆字符（0/O、1/I/L），分段显示 `XXXX-XXXX-XXXX-XXXX` | 减少客服 |
| 校验位 | 末位加校验字符 | 前端先拦掉输错的，减少无效请求 |
| 数据库存储 | 只存 **HMAC/哈希**（带服务端 pepper），不存明文 | 数据库泄漏也无法直接使用 key |
| `encrypted_key` 列 | ⚠️ 仅在你**确实需要"重新展示 key 给用户"**时才保留，并用服务端密钥加密；加密密钥不得放在数据库或 ZIP 里 | 可逆存储 = 额外攻击面 |
| 卡网用的明文 key 批次文件 | 上传卡网后**加密归档或销毁**，不要长期留在电脑/网盘/聊天记录里 | 这是最常见的泄漏来源 |
| 唯一性 | 数据库层加唯一约束 | 不要依赖应用层判断 |

### 4.3 激活协议（建议）

1. 扩展生成 `device_id`（本地随机 UUID + 浏览器/系统指纹的哈希，**不要采集个人信息**）。
2. 用户输入 key → 调用 Edge Function `activate(key, device_id, app_version)`。
3. 服务端校验：key 存在、状态为 sold/activated、未过期、设备数未超限、请求频率正常。
4. 成功则返回一个**签名后的授权令牌**（例如 Ed25519 签名的 JSON：`key_id`、`plan`、`features`、`device_id`、`exp`）。
5. 扩展内置**公钥**验证令牌签名；私钥只在服务端。
6. 扩展每隔 N 天（如 3–7 天）静默续期；网络失败时有**宽限期**（如 72 小时）仍可使用。
7. 退款/吊销 → 下次续期失败 → 扩展锁定，并提示用户联系你。

> **为什么用签名令牌而不是"查到 status=active 就放行"？**
> 因为后者会让扩展每次都必须在线、且逻辑全在客户端的 `if` 里，极易被改。签名令牌至少保证"授权内容不是用户自己能伪造的"，并且支持宽限期。

### 4.4 现实判断：防共享 vs 防破解

| 威胁 | 能防吗 | 手段 |
|---|---|---|
| 普通同学把 ZIP 发给朋友 | ✅ 能 | 没有 key 就不能用 |
| 把 key 发给朋友一起用 | ✅ 大部分能 | 设备数限制（如 1–2 台）、异常设备告警、可解绑次数限制 |
| 有技术的人改 JS 绕过检查 | ❌ **不能完全防** | 只能提高成本：混淆、多处校验、关键参数来自服务端 |
| 把破解版/改版 ZIP 传播 | ❌ 不能完全防 | 把"打卡所需的关键数据/步骤"依赖服务端令牌；不断更新让旧版失效 |

**务必接受的现实**：纯客户端的扩展**永远可能被破解**。你的目标不是 100% 防盗，而是：**让正版比盗版方便**，并把盗版的"生命周期"压短。
真正稳的保护是：**把有价值的部分放在服务端**。手机通知服务天然在服务端，这是它作为"付费功能"的结构性优势。

可行的"提高破解成本"的做法（按性价比排序）：
1. 令牌签名验证 + 多个检查点（不要只在启动时检查一次）。
2. 核心功能所需的某个参数/配置由服务端令牌下发（例如目标站点的适配规则/选择器配置）。
3. 版本强制升级（`min_version`）：旧版被破解后，下一个版本让它失效。
4. JS 混淆/打包压缩（只能拖慢，不能阻止）。

### 4.5 防暴力破解与滥用

- 激活接口限流：按 IP、按设备、按 key 前缀；连续失败后指数退避。
- 返回信息统一（不要区分"key 不存在"与"key 已被使用"到可枚举的程度）。
- 启用 Cloudflare/Vercel 防护或 Supabase 自带的限流方案；监控异常峰值并报警。
- 记录失败尝试，定期人工检查。

### 4.6 离线与宕机

- 激活/续期服务一旦宕机，**必须不让已激活用户立刻失效**（宽限期 + 本地缓存令牌）。
- 打卡发生在"关键时刻"（上课时间）。如果此刻验证失败导致打卡失败，用户损失很大。**宁可宽松，也不要因为验证服务抖动而误伤付费用户。**
- 监控：为激活接口加外部探活（如 UptimeRobot 之类），失败时通知你的手机。

### 4.7 版本管理与远程开关（强烈建议）

ZIP 分发的最大隐患：**用户不会自动更新**。建议扩展启动/续期时读取一份"远程配置"：

```json
{
  "min_version": "1.4.0",
  "latest_version": "1.5.2",
  "announcement": "目标网站已改版，请更新到 1.5.2",
  "kill_switch": false,
  "feature_flags": { "phone_notify": true }
}
```

用途：目标网站改版时快速公告；强制淘汰有 bug 的旧版；出现严重问题（法律/投诉）时**紧急停用**。**没有它，你就没有刹车。**

### 4.8 两个渠道的差异（容易被忽略）

| 项目 | 自建网站 | 卡网 |
|---|---|---|
| 买家身份 | 有邮箱/订单 | 通常**匿名**，你拿不到联系方式 |
| key 发放 | 你的服务器支付后发放 | 卡网从你预上传的库存中发放 |
| 退款 | 你可通过 Stripe/ToyyibPay 退款并吊销 | 退款流程由卡网规则决定，你很难主动联系买家 |
| 状态同步 | 实时 | **你不知道哪个 key 何时被卖出**，只能在"被激活"时才知道 |
| 对账 | 订单 ↔ 支付 ↔ key 三方对账 | 卡网后台销量 ↔ 你的激活数，只能事后比对 |

**建议**：在 `license_keys` 里加 `channel` 字段，并定期（每周）把卡网后台销量与"已激活 key 数"做比对；对卡网渠道的 key 设置**首次激活截止期**（如 90 天），避免库存 key 被盗卖/泄漏后长期有效。

## 5. 支付系统评估

### 5.1 通用原则（适用于所有支付渠道）

1. **"支付成功页"不是发货依据，Webhook 才是。** 用户可能关页面、刷新、断网。
2. **Webhook 必须幂等**：用 `event_id` / `payment_id` 做唯一键，重复收到同一事件不能重复发 key。
3. **必须验证签名**（Stripe 有签名头；ToyyibPay 见 5.3）。
4. **订单状态机**：`created → pending → paid → fulfilled → refunded / disputed / failed`，不要用一个布尔值 `paid` 解决一切。
5. **金额与币种以服务端为准**，不要信任前端传来的价格。
6. **对账任务**：每天比对 "支付平台已付款订单" vs "你库里已发放的 key"，不一致就报警（付了钱没 key 是客诉与争议的最大来源）。
7. **保存证据**：支付时间、IP、User-Agent、同意条款的记录（勾选"我已阅读退款政策"并记录时间），这是日后应对争议的核心材料。

### 5.2 Stripe（马来西亚账户）

| 优点 | 缺点 / 风险 |
|---|---|
| 国际卡、Apple/Google Pay 体验好；文档、webhook、测试工具成熟 | 对**产品类型**审核严格，账户被限制/冻结时资金可能被 hold |
| 争议（chargeback）流程成熟、有证据提交系统 | **争议费用高**：每次争议会收取"争议费"，且 2025-06 起若你选择应诉还会另收"应诉费"（赢了会退还应诉费）。✅ 多个来源显示马来西亚（MYR）账户的争议费明显高于美国的 US$15，具体数额以 Stripe 定价页为准 |
| 可在争议前**全额退款**来避免被拒付 | 即使你赢了争议，该争议仍会计入你的争议率（✅ 来源明确）；争议率高会被卡组织监控 |
| Radar 基础风控默认开启 | 退款时通常**不退还原手续费**（⚠️ 请核实当前政策） |

**关键技巧**
- 用户要求退款 → **主动全额退款通常比被争议更便宜**（避免争议费 + 保护争议率）。
- 在 Stripe 账单描述（statement descriptor）里写**用户认得出的名字**，否则用户看不懂账单会直接向银行投诉（"不认识这笔交易"是最常见的拒付原因）。
- 开启 Stripe 的邮件收据，并在收据/成功页明确写产品名、退款政策、客服联系方式。

### 5.3 ToyyibPay

✅ 已核对公开定价页（2026-10）：

| 项目 | 内容 |
|---|---|
| 币种 | **仅 MYR** |
| FPX 费用（Standard） | 约 RM1.00/笔（B2C）；另有 Madani 档约 RM0.80/笔，需另付提现费等 |
| 卡支付 | 通过合作方：本地卡约 1.5%，外国卡约 3.5%，另有一次性开通费与年费 |
| 结算 | 视档位 1–7 个工作日（"尽力而为"） |
| 账户状态 | 你目前是 "Unverified User"：**可收款，但结算要等验证完成**（你记录的是完整提交后 3–7 个工作日） |

**优点**：马来西亚本地用户熟悉 FPX；定额手续费对中高客单价友好。
**缺点 / 风险**

| 风险 | 说明 / 建议 |
|---|---|
| 小额订单手续费占比高 | 若单价只有 RM9–15，每笔 RM1 = 7–11% 的成本，再叠加退款（⚠️ 通常手续费不退） |
| 回调（callback）不可盲信 | ⚠️ 不要仅凭回调参数判定"已付款"；**务必在服务端用订单号再向 ToyyibPay 官方接口查询一次账单状态**再发 key |
| FPX 退款流程偏人工/偏慢 | 提前弄清楚退款方式、时效、是否扣费，并写进你的退款政策 |
| 未验证期间资金卡住 | 在验证完成前，**不要大规模推广、不要承诺"即时退款"**——你手里没有这笔钱 |
| 单一币种 | 海外用户不适用，需要靠 Stripe |
| 技术文档/生态相对薄 | 自己多做防护：重试、超时、幂等、日志 |

### 5.4 卡网（368云寄售）

| 优点 | 缺点 / 风险 |
|---|---|
| 对中国区买家友好（支付宝/微信），不需要你自己接支付 | **平台风险**：封店、规则变更、提现受限、跑路，都不在你控制范围 |
| 自动发货，省人工 | 买家匿名，退款/客服/更新通知困难 |
| 无需你处理支付合规 | 你无法实时知道销量，库存与你库里的 key 状态不同步 |
| 引流（有些卡网自带流量） | 手续费、提现周期、争议规则以卡网为准（⚠️ 请把当前费率与结算周期写进你的成本表） |

**建议**
- 把卡网当作"可替换的渠道"，**不要让业务依赖它**。
- 卡网上的商品描述要与实际功能一致；退款政策要在商品页写清楚（卡网上同样会发生纠纷）。
- 在卡网渠道的 key 上加 `batch_id`：一旦某批 key 泄漏，可整批吊销。

在定价前，用一张表算清楚"每单到手多少"：

| 渠道 | 客单价 | 手续费 | 退款概率 × 退款损失 | 预估到手 |
|---|---|---|---|---|
| Stripe（国际卡） | ? | % + 固定费 | ? | ? |
| ToyyibPay FPX | ? | RM1 | ? | ? |
| 卡网 | ? | ? | ? | ? |

**特别提醒**：手机通知服务若是订阅制，其收入必须**覆盖服务器成本 + 客服成本 + 退款损耗**，否则用户越多你越亏（见第 7 节）。

### 5.6 备用支付方案

- 定期把资金提到自己的银行账户，不要长期留在支付平台余额里。

## 6. 退款、争议、客诉

### 6.1 退款政策（必须在购买页明文、并让用户勾选同意）

建议明确这些条款：

| 条款 | 建议写法（示意） |
|---|---|
| 适用对象 | 数字产品（授权密钥 + 软件使用权） |
| 可退款条件 | 例如：**购买后 X 天内且 key 未激活**；或因产品本身故障且在 X 天内无法修复 |
| 不可退款 | 已激活且已正常使用；因目标网站变更导致的"暂时不可用"（应改为**补偿/延长有效期**而非退款，视你的承诺而定）；因用户自身设置/账号问题导致的失败 |
| 退款方式与时效 | 原路退回；各渠道处理时间不同；手续费是否扣除 |
| 退款后果 | key 被吊销、设备解绑、手机通知服务停止 |
| 服务可用性声明 | **不保证每次都成功打卡**；不对因打卡失败产生的任何后果负责（需律师润色） |

> ⚠️ 单靠"不退款"条款**不能**阻止银行端的争议。持卡人向银行提出争议时，银行不一定遵循你的条款。你的真正保护是：**证据 + 良好的客服 + 合理的退款流程**。

### 6.2 争议（chargeback）证据清单

提前设计好系统，**让证据自动留存**：
- 订单时间、金额、币种、买家邮箱
- 购买时勾选同意条款的时间戳与版本号
- key 发放时间
- **首次激活时间、IP、设备信息、使用记录**（"用户确实在使用"是数字商品争议中最有力的证据）
- 客服往来记录

### 6.3 退款后的联动（自动化，不要靠人记）

退款 webhook → ① 订单置为 `refunded` → ② 对应 key `revoked` → ③ 令牌下次续期失败 → ④ 手机通知服务停止并回收资源 → ⑤ 记 `audit_log` → ⑥（可选）通知你。

### 6.4 退款/争议率的管理

- 卡组织对争议率有监控门槛（⚠️ 一般在 1% 附近会触发关注，具体以 Stripe/卡组织规则为准）。**早期订单量少时，几笔争议就能让比例很难看**——这是新手最容易忽略的数学。
- **预留准备金**：把前几个月收入的一部分留着，不要立刻花掉。
- 主动退款优于被动争议（见 5.2）。
- 提供明显的客服入口（WhatsApp/Telegram/邮箱）并及时回复；很多争议其实是"找不到人"造成的。

### 6.5 最可能引发"集体退款"的情景

| 情景 | 概率 | 影响 | 预案 |
|---|---|---|---|
| 目标网站改版导致扩展失效 | 高 | 全体用户 | 远程公告 + 快速热修复 SLA + 延长有效期作为补偿 |
| Supabase/Vercel 事故导致无法激活 | 中 | 新老用户 | 宽限期、监控、状态页 |
| 学校发现并处分用户 | 低-中 | 个别用户，但会传播 | 见第 8 节 |
| 破解版出现，价格崩盘 | 中 | 收入 | 版本迭代 + 服务端能力 |

## 7. 手机通知服务（服务器开通）

### 7.1 你目前的想法

"目前可能会通过服务器给用户开通"。

### 7.2 优点

- 天然在服务端，**防盗用能力强**，适合作为付费功能。
- 订阅制（学期/年度）收入可预测。
- 可作为"增值服务"提高客单价。

### 7.3 缺点 / 风险

| 风险 | 说明 | 建议 |
|---|---|---|
| **人工开通不可扩展** | 每笔订单都要你手动开通，漏开/错开几乎必然发生 | **自动化**：支付 webhook → 写入 `entitlements` 表 → 服务器按表推送 |
| 持续成本 | 服务器、域名、推送通道、监控，**用户不付钱时也在花钱** | 先算清盈亏平衡点：每位订阅用户的月均成本 × 预估用户数 |
| 到期/续费/退款联动 | 订阅到期要自动停止；退款要自动回收 | `valid_until` 字段 + 定时任务 |
| 单点故障 | 你的服务器挂 = 付费用户收不到通知 = 退款 | 监控、自动重启、简单的健康检查；明确"尽力而为"的承诺 |
| 推送通道可靠性 | 第三方推送服务（FCM、Telegram、Bark 等）有各自限制和中断 | 选择方案时优先考虑稳定性与你的可控度；准备失败重试与告警 |
| 隐私 | 你可能保存设备 token、手机号、学号或打卡记录 | **最小化收集**；不存储不必要的敏感数据；写隐私政策；考虑马来西亚 PDPA 的要求（⚠️ 请咨询专业人士） |
| 承诺过度 | "及时提醒"一旦漏提醒，用户的损失比订阅费大得多 | 条款中写明"尽力而为、不保证到达" |
| 学期型套餐的时间定义 | "Semester/Yearly" 的起止日期如何算？用户中途买？ | 用"自激活起 N 天"，不要依赖学校学期历法（你已经去掉了 Degree Pass，因为课程长度不一，方向正确） |

### 7.4 建议的数据模型思路

把"用户买了什么"抽象为**权益（entitlement）**，而不是散落在各处的布尔值：

```
entitlements
  id, key_id / user_id, feature('core' | 'phone_notify'),
  valid_from, valid_until, status, source_order_id
```

- 基础功能和手机通知都是权益；激活令牌里的 `features` 来自这里。
- 服务器推送前只看一件事：该设备/用户在 `entitlements` 中此刻是否有效。

### 7.5 补充：ntfy 订阅频道方案的专项评估（2026-10-06 新增）

**你的实现**：付款后扩展内显示二维码 → 用户扫码 → 跳转 ntfy App → 订阅你的频道（topic）→ 之后收到通知。

**好消息（相比我之前担心的）**
- 你**不需要收集手机号、设备 token、推送凭证**——隐私风险和合规负担明显降低。
- 开源、成本低，用户端安装门槛低（扫码即订阅）。
- 订阅关系由用户的 App 自己维护，你不用管理设备注册。

**但 ntfy 的安全模型和你的"付费功能"设计有几处关键冲突：**

| # | 风险 | 说明 | 建议 |
|---|---|---|---|
| N1 | **topic 名称就是"密码"** | ntfy 的 topic 默认没有访问控制（公共服务器上更是如此）：**任何知道 topic 名的人都能订阅并读取，也能往里发消息**。所以 topic 必须是**不可猜测的长随机串**（≥128 bit），且视为密钥 | 每个权益生成一个独立的随机 topic，存入 `entitlements.notify_topic`；**不要**用 key 的哈希、学号、邮箱、递增数字推导 topic，除非使用服务端私密盐做 HMAC |
| N2 | **二维码 = 可转发的订阅凭证** | 用户把二维码/链接发给同学，对方免费订阅同一个频道 | 公共 ntfy 无法限制订阅者数量。要防共享，需要**自建 ntfy 并开启认证**（用户/令牌/ACL），或接受"共享通知"这个漏洞并把它计入定价 |
| N3 | **退款后无法撤销订阅** | 公共 topic 一旦被订阅，你没法踢人，只能**轮换 topic**（让合法用户重新扫码）或停止发送 | 设计"轮换 topic"流程：退款/到期 → 作废旧 topic → 如需继续服务则发新 topic 并让扩展重新展示二维码 |
| N4 | **"付费功能"可能根本没有被保护** | 如果通知是**扩展在浏览器里直接** `POST` 到 ntfy 的，那任何人都能用免费的 ntfy 自己建 topic、自己改扩展代码发送——这个功能就不是付费功能了 | 让扩展调用**你的服务端**（带签名授权令牌），由服务端校验权益后再转发给 ntfy；扩展里**不保存**能直接发布的凭证 |
| N5 | **通知内容泄漏** | 如果 topic 被猜到/转发，通知内容会被陌生人看到 | 通知正文**不要含**学号、姓名、课程全称、账号等敏感信息；用"打卡成功/失败 + 时间"这类最小信息 |
| N6 | **公共实例的限额与可用性** | ⚠️ ntfy.sh 对匿名发布有速率与每日限额，缓存保留时间有限，且服务是第三方运营，政策可能变化 | 请核对 ntfy 官方文档当前限额；用户量上来后考虑**自建实例**或购买付费计划（可保留 topic） |
| N7 | **iOS 即时推送限制** | ⚠️ 自建实例时，iOS 要做到及时推送通常需要配置上游转发到 ntfy.sh（`upstream-base-url`）；Android 受省电策略影响也可能延迟 | 在 FAQ 写清楚"需关闭省电限制/允许通知"；把产品承诺写成"尽力而为" |
| N8 | **服务端凭证泄漏** | 若使用带认证的 ntfy，你服务端的发布令牌泄漏 = 任何人可以冒充你给所有用户发通知 | 令牌只在服务端环境变量；定期轮换；按用途分离令牌 |
| N9 | **二维码出现的时机与来源** | 二维码必须由**服务端在校验权益后**下发，不能由扩展本地根据 key 计算 | `refresh` 令牌里带 `features` 与（加密/签名的）`notify_topic`，或由 `status` 接口返回 |

**推荐的两档方案**

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 起步版（公共 ntfy + 随机 topic + 服务端转发）** | 随机长 topic；扩展 → 你的服务端 → ntfy；退款时轮换 topic | 零额外基础设施，成本最低 | 二维码可被转发；公共实例限额与可用性不在你控制 |
| **B. 加固版（自建 ntfy + 认证）** | 自建实例，每用户独立令牌/ACL；退款时直接撤销令牌 | 可防共享、可吊销、可控限额 | 要运维一台服务器；iOS 需配置上游转发；增加故障点 |

> 我的建议：**先用 A 上线并限量**，同时把"topic 轮换"和"服务端转发"这两件事一开始就做对（它们是之后升级到 B 的基础）；当订阅用户到一定规模或出现明显的共享问题，再迁移到 B。

**数据模型补充**

```
entitlements 增加：notify_topic（随机、唯一）、notify_rotated_at、last_notify_at、notify_fail_count
```

**测试用例（务必覆盖）**
- 退款 → 旧 topic 轮换后，旧订阅者收不到新消息
- 同一 topic 被多人订阅时，系统有无异常告警（至少看得到订阅数异常：自建版可见，公共版基本不可见）
- 扩展离线/服务端离线时，通知失败是否被记录并可重试
- 通知内容中不含敏感字段

### 7.6 补充：已确认的通知链路评估（2026-10-06 新增）

**你的实际链路**

```
扩展（打卡结果）──同步──▶ 云端通知队列（Supabase）
                              │
                    notification-worker（服务端）
                    ① 检查手机提醒授权（entitlement）
                    ② 向 ntfy.sh 发布到该用户的 topic
                              │
                         手机 ntfy App 接收

另一条独立路径：扩展本身 → Chrome 本机通知（基础功能，不经过服务器）
```

**判断：架构形状是对的。** 服务端把关授权后再转发，7.5 中的 **N4（付费功能被客户端绕过）基本被解决**；队列结构也天然支持重试和审计；"本机通知免费 + 手机通知付费"的分层也清晰、容易向用户解释。

**还需要核实/补强的地方**

| # | 风险点 | 说明 | 建议 |
|---|---|---|---|
| Q1 | **扩展怎么写入队列？** | 如果是扩展用 `anon key` 直接 `insert` 队列表，任何人都能往队列里灌数据（刷爆成本、伪造通知、冒充他人的 topic） | 只允许通过 Edge Function 写入，并要求**签名授权令牌**；队列表对 `anon` 零权限；按权益做速率限制 |
| Q2 | **授权检查要做两次** | 入队时检查一次，**发送时再检查一次**（入队后可能已退款/到期/吊销） | worker 发送前重新读取 `entitlements`；失效则标记 `dropped` 并记录原因 |
| Q3 | **重复发送** | worker 重试、函数超时重跑，会让用户收到重复通知 | 每条通知带 `idempotency_key`（例如 `entitlement_id + 事件id`）；状态机 `queued → sending → sent / failed / dropped`；"领取任务"用原子更新（`FOR UPDATE SKIP LOCKED` 或带条件的 `UPDATE ... RETURNING`） |
| Q4 | **过期通知比不通知更糟** | worker 宕机恢复后一次性补发几小时前的"打卡成功"，会误导用户 | 每条通知设 `expires_at`（如 15–30 分钟），过期不发，只记录 |
| Q5 | **worker 如何被触发** | Supabase 没有常驻进程；通常是 DB Webhook/触发器、`pg_cron` 定时拉取或 Edge Function 调度。轮询过密会消耗函数调用量，过疏会延迟通知 | 优先"入队即触发"+ 低频 cron 兜底扫描；监控队列积压长度与最老消息年龄并报警 |
| Q6 | **ntfy.sh 对你服务端的限流** | ⚠️ 向公共实例匿名发布受限额约束，且 Supabase Edge Functions 的出口 IP 可能是共享的，有被其他租户"连累"限流的可能性（需实测确认） | 使用带账号/令牌的发布方式；上线前压测；用户量增长后评估付费计划或**自建 ntfy** |
| Q7 | **"已发送" ≠ "已送达"** | ntfy 接受发布只代表服务器收到，手机是否收到取决于网络、省电策略、App 状态 | 后台只显示"已发送"；对用户的承诺写成**尽力而为**；FAQ 写明省电设置 |
| Q8 | **队列里存了什么** | 你把"打卡结果等通知"同步到了云端——这是**用户使用数据**进入你的数据库 | 只存最小字段（结果/时间/通用文案），**不存学号、账号、完整课程名**；发送后短期保留（如 7–30 天）再删除；RLS 限定仅本人/服务端可读；隐私政策里写明 |
| Q9 | **最关键的告警恰恰是"没有任何打卡"** | 浏览器关了、电脑睡眠了，扩展根本不会运行，也就没有"失败通知"可发 | 可选的高价值功能：**心跳/缺席告警**——服务端在预期时间窗内没收到扩展心跳，就主动给手机发提醒。这是纯服务端能力，既防盗用又是真正的卖点 |
| Q10 | **成本与滥用上限** | 每条通知 = 一次 DB 写入 + 一次函数调用 + 一次 ntfy 发布 | 每权益每日通知上限；队列长度上限；异常用量自动暂停并告警 |
| Q11 | **topic 安全仍然适用** | N1–N3、N5 依然成立：topic 必须是长随机串、二维码可被转发、退款需轮换 topic、通知正文要最小化 | 同 7.5 |

**新增测试用例**
- 入队后立刻退款 → worker 发送前检查失败，通知被丢弃
- 同一通知被 worker 重复领取/重试 → 用户只收到一条
- worker 宕机 1 小时后恢复 → 过期通知不补发
- 用 `anon key` 直接向队列表插入 → 必须失败
- 一个令牌高频入队 → 被限流
- ntfy.sh 返回 429/5xx → 进入退避重试，最终标记 `failed` 并可在后台看到

## 8. 法律、合规与平台风险（最大的非技术风险）

> 我不知道你的目标签到系统具体是什么，也不对其做合法性判断。但从**商业风险**角度，下面这些必须被认真对待，因为它们决定了你的收款账户、平台账号和用户是否会同时出事。

### 8.1 支付机构与平台

| 风险 | 说明 |
|---|---|
| 产品描述与真实功能不一致 | 你之前向 HitPay 描述的是"浏览器扩展 SaaS 工具（面向学生）"。向 Stripe/ToyyibPay/卡网提交的描述**必须真实、一致**。如果日后被审查发现与实际功能出入大，后果通常是**封号 + 冻结资金**，比一开始被拒绝严重得多 |
| 受限业务条款 | 支付机构通常禁止"协助欺骗/规避系统规则"类产品。**请逐条阅读 Stripe、ToyyibPay、卡网的禁止业务条款，并判断你的产品是否落入灰色地带** |
| 账户审核 | 业务主体（个人 vs 公司）、网站内容（条款/隐私/退款/联系方式）是否齐全，都会影响审核与账户稳定性 |
| 卡网平台 | 平台规则变化、下架、封店，都是你无法对抗的风险 |

### 8.2 目标系统（学校/机构）与用户

| 风险 | 说明 |
|---|---|
| 违反目标系统的使用条款 | 自动化、脚本化访问可能被禁止；学校可能封禁账号、更改机制、甚至向你发出通知 |
| 用户后果由谁承担 | 如果用户因使用工具被处分，**他们会找你**：投诉、要求赔偿、在社交平台曝光。这同时会反噬你的支付账户 |
| 产品寿命不由你决定 | 目标系统一改版，产品就失效；你卖的其实是"在某个时间窗口内有效的适配" |
| 资料保护 | 若你的扩展接触到用户的学校账号/Cookie/学号，你就承担了**保管责任**；一旦泄漏，影响远超软件价格 |

### 8.3 建议

1. **读目标系统的使用条款**，并如实评估；必要时咨询律师。
2. **产品措辞保持诚实**：描述为用户本人有权使用的自动化/提醒工具，不夸大、不做"保证打卡成功"之类的承诺。
3. **不收集用户的学校账号、密码、Cookie**；任何敏感数据只在本地处理，不上传服务器。
4. 在使用条款中明确：用户须自行遵守其所在机构的规定，**使用后果由用户自行负责**（需律师确认写法）。
5. 准备**应急预案**：被机构投诉/通知时，你能在 24 小时内通过远程开关（4.7）停用并下线商品页。
6. 如果有可能，**把产品定位调整为更"安全"的方向**（例如以"提醒/通知"为核心卖点，把自动操作作为可选项），长期风险会低很多。——这是商业判断，由你决定，但值得认真考虑。

### 8.4 其他合规项（⚠️ 请咨询专业人士）

- **主体与税务**：个人收入申报、是否注册公司（SSM）、是否涉及服务税（SST）等。
- **消费者保护**：马来西亚对电子交易/数字商品有披露要求（商家名称、联系方式、价格、退款条款等）；若你面向海外用户，还会有各地区的规定（如欧盟的数字内容撤销权）。
- **隐私**：隐私政策与个人资料处理说明；Cookie 说明；数据保留期限。
- **未成年人**：学生用户可能未满 18 岁，注意相关条款与支付安全。
- **扩展分发**：ZIP 加载"开发者模式"扩展，Chrome 可能在启动时弹出"禁用开发者模式扩展"提示，用户可能因此误认为有风险——这会带来客服与退款。准备**图文安装教程**与常见问题。

### 9.4 AI 生成代码的审查（重要）

你的系统大量由 Codex 生成。支付与授权属于"出错成本很高"的代码，建议：
1. **写测试**：至少覆盖 webhook 重复、乱序、退款、过期、并发激活。

3. **分环境验证**：用 Stripe test mode / ToyyibPay 沙盒完整走一遍"购买→发 key→激活→退款→吊销"。
4. **不要信"看起来能跑"**：并发和边界情况才是支付系统出事的地方。

### 12.2 接口（Edge Functions）

| 函数 | 作用 |
|---|---|
| `activate` | 校验 key、绑定设备、发签名令牌 |
| `refresh` | 续期令牌；检查吊销/到期/最低版本 |
| `deactivate` | 用户自助解绑设备 |
| `webhook-stripe` | 验签 → 幂等 → 更新订单 → 发 key / 处理退款与争议 |
| `webhook-toyyibpay` | 回调 → 主动查询确认 → 同上 |
| `config` | 返回远程配置（公告、最低版本、开关） |
| `status` | 用户查询 key 状态（限流） |

### 12.3 端到端流程（网站渠道）

```
用户下单 → 创建 order(pending) → 跳转 Stripe/ToyyibPay
→ 支付平台 webhook → 验签/二次查询 → 幂等写入 payment
→ 分配一个 sold 状态的 key（行级锁/唯一约束）→ 邮件发送 key（并在成功页展示）
→ 用户激活 → 设备绑定 → 返回签名令牌
→ 若购买手机通知 → 写入 entitlements(phone_notify, valid_until)
→ 服务器按 entitlements 推送
→ 退款 webhook → key revoked + entitlements 失效 + 审计
```

### 12.4 卡网渠道流程

```
你批量生成 key → 写入库(status=listed, channel=kawang) → 明文批次上传卡网 → 加密归档/销毁明文
→ 买家在卡网购买 → 卡网展示 key
→ 买家在扩展中激活 → 服务端首次看到该 key：status listed→activated，记录 first_activated_at
→ 每周对账：卡网后台销量 vs 已激活数
→ 超过首次激活截止期仍未激活的 key：标记并关注是否泄漏/被倒卖
```
